        The Library Migration Kit & Agent Protocol (LMKAP/1.0)
     A dependency-bot-style framework for versioned client migration
                     across breaking contract changes


Status of This Memo

   This document specifies a framework by which a versioned software
   library ships, alongside each breaking release, a self-contained
   "migration kit" that a human OR an autonomous coding agent can run to
   migrate a consuming codebase — deterministically, verifiably, and
   without the library author being in the loop.

   It is written as a forward-looking, full-system specification. Parts
   marked [IMPLEMENTED] exist today in the reference implementation
   (github.com/ab0t-com/auth-sdk-go, migrations/). Parts marked [SPEC]
   are specified for future implementers and are not yet built. The
   distinction is deliberate: the value of this RFC is that the pieces we
   have and the pieces we don't share ONE contract, so nothing built
   later has to be retrofitted.

   Distribution of this memo is unlimited. It is versioned (see the
   header and Appendix D); a change to any normative section MUST bump
   this document's version.


Abstract

   A breaking change in a widely-embedded library is a coordination
   problem: the author knows exactly what changed and why, but every
   consumer must rediscover it, one 422 or compile error at a time.
   Dependency bots solve version BUMPS but not CONTRACT changes — they
   can raise "v2 is available" but cannot tell you that `.URL` is now
   `.Endpoint` only where the value is an EventSubscription, nor apply
   it, nor prove it worked.

   LMKAP closes that gap. Each breaking release carries a kit: a
   machine-readable rule manifest, a read-only checker, human docs, and
   an agent protocol. A checker locates every affected call site with
   its fix; an agent (or a person) applies the fixes, re-checks, builds,
   and writes an auditable worklog; CI gates on the checker. The kit is
   the migration, versioned and shipped WITH the code that necessitated
   it.

1.  Introduction

1.1.  Motivation

   Twice in the reference library, a client discovered a breaking
   contract change the hard way: a request field the server had renamed
   (a silent 422) and a response type the client mis-modeled (a silent
   whole-response decode failure). In both cases the AUTHOR already knew
   the exact delta. The cost was pure coordination loss. A third pattern
   is worse: teams who "hand-rolled" a client because the SDK was thin
   reproduce every gap, and a version bump never reaches them at all.

   The lesson: the migration is knowledge the author has and the
   consumer needs, and it should travel WITH the release as an
   executable artifact — not as a changelog paragraph a human re-derives.

1.2.  Design principles

   P1  The kit ships WITH the release that needs it, in-tree, versioned.
   P2  Every claim is VERIFIABLE by the consumer without trusting prose:
       a checker that exits non-zero until clean, and a compiler/test
       run as ground truth.
   P3  READ-ONLY discovery, EXPLICIT application. Finding what to change
       never edits code; applying is a separate, reviewable step.
   P4  Machine-readable FIRST, human-readable ALSO. Tools, agents, IDEs,
       and CI consume the same rules a person reads.
   P5  Type-scoped, not textual. A rule targets `.URL` on an
       EventSubscription value, not the string ".URL" everywhere.
   P6  Behavioural changes are FLAGGED, never auto-applied. A semantic
       change (e.g. an authorization call that now fails closed) is for
       a human to reason about.
   P7  The agent is a CLIENT of the kit, not the kit. Any conforming
       agent — or a person — runs the same protocol.
   P8  No-merge, no-surprise. The migration opens a change for review;
       it never merges or releases on the consumer's behalf.

1.3.  Terminology

   The key words MUST, MUST NOT, REQUIRED, SHALL, SHOULD, SHOULD NOT,
   MAY, and OPTIONAL in this document are to be interpreted as described
   in RFC 2119.

   KIT      A versioned directory migrating a consumer across one
            release boundary (FROM -> TO).
   MANIFEST A machine-readable description of a KIT's rules (kit.json).
   CHECKER  An executable that locates affected call sites, read-only.
   RULE     One typed transformation (rename / remove / add / retype /
            behavioural).
   TARGET   The consuming codebase being migrated.
   AGENT    Any actor (human or autonomous) executing the AGENT PROTOCOL.
   WORKLOG  The append-only record an AGENT writes into the TARGET.
   FINDING  One located occurrence in the TARGET that a RULE matches.


2.  Architecture Overview

        LIBRARY REPO (author side)          CONSUMER REPO (target side)
        ------------------------            ---------------------------
        release vTO  ── ships ──▶  migrations/vFROM-to-vTO/
                                     ├── kit.json      (manifest) [SPEC]
                                     ├── migrate-check.sh (checker)
                                     ├── MIGRATION.md  (human detail)
                                     ├── MIGRATION.SOP.md (procedure)
                                     ├── agent-cycle-prompt.md
                                     └── CLIENT_NOTICE.md
                                            │
                       ┌────────────────────┼────────────────────┐
                       ▼                    ▼                    ▼
                  CI (gates on         AGENT (loop +        PERSON (SOP,
                  checker --strict)    worklog)             same loop)
                       │                    │                    │
                       └──────── all read the SAME rules ────────┘
                                            │
                                            ▼
                                 TARGET edited → build/test → PR
                                 (never merged, never pushed by the kit)

   A KIT is the single source of truth. CI, agents, and people are all
   CLIENTS of it. The checker is the shared, machine-readable interface
   between "what changed" and "did I fix it".


3.  The Migration Kit

3.1.  Directory and naming

   A KIT MUST live in the library repository under:

       migrations/v<FROM>-to-v<TO>/

   where <FROM> and <TO> are the exact release identifiers (e.g.
   "0.9.2", "0.10.0"). One KIT covers exactly one release boundary.
   Consumers crossing multiple boundaries apply KITs in order
   (Section 6). A top-level migrations/README.md SHOULD index the KITs.
   [IMPLEMENTED: migrations/v0.9.2-to-v0.10.0/, v0.10.0-to-0.10.1/]

3.2.  Required and optional artifacts

   A conforming KIT MUST contain:

     migrate-check.sh   The CHECKER (Section 3.4).           REQUIRED
     MIGRATION.md       Human before->after for every rule.  REQUIRED

   A conforming KIT SHOULD contain:

     kit.json           The MANIFEST (Section 3.3).          [SPEC]
     MIGRATION.SOP.md    Step-by-step procedure w/ rollback. [IMPLEMENTED]
     agent-cycle-prompt.md  Paste-ready agent loop.          [IMPLEMENTED]
     CLIENT_NOTICE.md    Broadcast text for consumers.       [IMPLEMENTED]

   Artifacts MUST NOT contain secrets, credentials, or the library's
   own server/implementation internals — a KIT is customer-facing.

3.3.  The Manifest (kit.json)  [SPEC]

   TODAY the rules live in the checker and in MIGRATION.md. The manifest
   promotes them to a first-class, machine-readable object so that a
   dependency bot, an IDE quick-fix, or a non-shell agent can consume
   them without parsing prose or a bash script. A conforming KIT SHOULD
   ship kit.json (Appendix B):

     {
       "lmkap": "1.0",
       "library": "github.com/ab0t-com/auth-sdk-go",
       "from": "0.9.2", "to": "0.10.0",
       "language": "go",
       "rules": [ <Rule>, ... ],
       "verify": ["go build ./...", "go vet ./...", "go test ./..."],
       "signature": "<detached signature over the canonical bytes>"
     }

   When kit.json is present it is NORMATIVE; migrate-check.sh and
   MIGRATION.md MUST be consistent with it (a conformance test SHOULD
   assert this in the library's own CI).

3.4.  The Checker Contract

   The CHECKER is the load-bearing interface. It MUST:

   (a) be READ-ONLY: it MUST NOT modify the TARGET;
   (b) accept a TARGET path as its first argument (default ".");
   (c) print, per FINDING, at least: file, line, the RULE it matched,
       and the exact fix;
   (d) exit 0 when there are zero actionable findings, and non-zero
       otherwise, so CI can gate on it;
   (e) be self-contained: no dependency beyond the target language's
       ubiquitous tooling (the reference uses bash + grep; a --json
       mode [SPEC] SHOULD emit structured findings for tools/agents);
   (f) prefer FALSE POSITIVES over false negatives, and SAY SO: common
       identifiers (`.ID`, `.Mode`) are flagged as CANDIDATES, and the
       consumer's clean build is the disambiguator (P5). A future
       type-aware checker [SPEC] SHOULD resolve the value's type to cut
       candidates to certainties.
   [IMPLEMENTED: bash+grep checker with candidate semantics + exit codes]

3.5.  Human documents

   MIGRATION.md MUST give, for every RULE, the before and after and a
   one-line "why". MIGRATION.SOP.md SHOULD give a numbered procedure
   with an observable expected-result and an on-failure branch per step,
   plus a ROLLBACK path (P8 requires reverting is always possible; for a
   library consumed by version this is "pin back to vFROM"). CLIENT_NOTICE
   SHOULD be copy-pasteable prose for a consumer who has not yet started.


4.  The Rule Language

   A RULE is a typed transformation. The five types cover the observed
   breaking-change taxonomy:

   RENAME     A field/selector is renamed (optionally value-remapped).
              e.g. `.URL` -> `.Endpoint`; value "allowlist" -> "allow".
   REMOVE     A field no longer exists; delete the reference.
   ADD-REQUIRED  A previously-absent field is now required on a request;
              the consumer MUST set it (no safe auto-value).
   RETYPE     A field's TYPE changed (string->number, slice->map). This
              is a code REWRITE at the use site, not a rename, and it is
              the class most likely to fail silently (whole-message
              decode failure), so RETYPE rules MUST carry an example of
              the real wire value.
   BEHAVIOURAL  Semantics changed with no source delta required (e.g. a
              call now fails closed). MUST be FLAGGED for human review;
              an AGENT MUST NOT auto-apply it (P6).

   Each RULE MUST carry a SCOPE (P5): the type/context in which it
   applies, so a matcher can (now: advise; future: enforce) that the
   selector belongs to the library's type and not the consumer's own.
   Each RULE SHOULD carry a CONFIDENCE: CERTAIN (type-resolved) or
   CANDIDATE (textual). A migration MUST NOT blanket-apply CANDIDATE
   rules; the build is the arbiter.

   [Example RULE, Appendix B. Reference taxonomy: the auth-sdk-go
   0.9.2->0.10.0 kit exercises all five types.]


5.  The Migration Agent Protocol

   Any AGENT (the reference migrationbot, a client's own coding agent, a
   future IDE action) executing a KIT MUST follow this protocol. It is
   identical to the human SOP; the SOP is this protocol for a person.

5.1.  Inputs and discovery

   An AGENT takes a TARGET and a KIT. If the KIT is not given, the AGENT
   SHOULD discover it: read the TARGET's pinned library version, and
   select the KIT whose FROM matches. Multiple boundaries -> Section 6.

5.2.  The Loop

   1. OPEN WORKLOG.   Create/append WORKLOG in the TARGET (5.3).
   2. BRANCH.         Work on a branch; if the tree is dirty, STOP and
                      report — never migrate over uncommitted work.
   3. CHECK.          Run the CHECKER. Log the finding count. If clean,
                      go to step 6.
   4. FIX.            Apply each FINDING's fix at its file:line. Apply a
                      CANDIDATE rule ONLY where the value's type is the
                      library type the rule names. RETYPE is a rewrite.
                      BEHAVIOURAL findings are NOT edited — noted for
                      step 7.
   5. RE-CHECK.       Re-run the CHECKER. If findings remain, go to 4.
                      The bar MUST NOT be lowered to force a pass.
   6. BUILD.          Bump the dependency to TO; run the KIT's `verify`
                      commands. Fix compiler-surfaced mismatches; re-run.
   7. REVIEW.         For each BEHAVIOURAL flag, review the affected
                      tests/call sites; update ASSERTIONS to the correct
                      new answer — never restore old behaviour.
   8. CLOSE.          Final WORKLOG entry; open a PR; DO NOT MERGE.

5.3.  The Worklog

   The AGENT MUST write an append-only WORKLOG (the reference names it
   MIGRATIONBOT_WORKLOG.md) into the TARGET. Every entry is in the shape
   CLAIMED -> DID -> VERIFIED. Corrections are new entries; past entries
   are never rewritten. The WORKLOG is the audit trail: a reviewer can
   reconstruct exactly what changed, why, and how it was proven.

5.4.  Stop conditions and failure handling

   Success is defined observably: the CHECKER exits 0 AND every `verify`
   command passes. An AGENT MUST NOT report success on a partial state.
   If a FINDING cannot be resolved, the AGENT MUST STOP and report it
   with its file:line rather than guess. An AGENT MUST NOT push to the
   library, and MUST NOT merge.


6.  Versioning and Chaining

   KITs are 1:1 with breaking release boundaries. A consumer crossing
   several boundaries (vA -> vD) applies KITs in order (A->B, B->C,
   C->D), re-verifying between each. A tool [SPEC] MAY compose a chain
   automatically; it MUST NOT skip a boundary. This RFC is itself
   versioned; a normative change bumps it (Appendix D). A KIT SHOULD
   declare the `lmkap` version it targets so an AGENT can refuse a KIT
   it does not understand.


7.  Integration

   CI          The CHECKER's exit code is a CI gate: a consumer adds
               `migrate-check.sh . && go build ./... && go test ./...`
               to block a merge that regresses onto an old contract.
   IDE  [SPEC] --json findings feed an editor quick-fix ("apply this
               rename here").
   BOT  [SPEC] A dependency bot that already opens "vTO available" PRs
               SHOULD, when a KIT exists, additionally run the KIT and
               attach the WORKLOG + checker output to the PR — turning a
               version-bump bot into a contract-migration bot.
   DISCOVERY [SPEC] `migratectl fetch <lib> <from> <to>` resolves and
               caches a KIT from the library's published tree.


8.  Trust and Security

   SIGNING [SPEC]  A KIT SHOULD be signed by the library's release key;
                   an AGENT SHOULD verify the signature before executing
                   a checker or applying rules, because a KIT is
                   executable content that edits a consumer's code.
   READ-ONLY       Discovery (the CHECKER) MUST NOT mutate the TARGET.
   NO-MERGE        Application opens a reviewable change; it MUST NOT
                   merge, push to the library, or release (P8).
   LEAST-TRUST     An AGENT running a KIT SHOULD be constrained to the
                   TARGET and the KIT; it MUST NOT touch the library
                   module.


9.  Extensibility

   LANGUAGE   The KIT layout, manifest, rule language, and agent
              protocol are language-agnostic; only the CHECKER and the
              `verify` commands are language-specific. A Python or
              TypeScript library ships the same shapes with a
              language-appropriate checker and verifier.
   HAND-ROLLED CONSUMERS  A consumer that does NOT import the library
              (a hand-rolled client of the same wire contract) cannot be
              migrated by source rules, but MUST be served by a
              published FIELD CONTRACT (the wire shapes) so it can
              conform. A KIT SHOULD reference that contract.
   NON-CODE   The framework generalizes to any versioned contract with
              locatable consumers (config schemas, API clients).


10.  Conformance Levels

   L1  MINIMAL:  a KIT with a conforming CHECKER + MIGRATION.md.
   L2  STANDARD: L1 + SOP + agent-cycle-prompt + CLIENT_NOTICE.
                 [the reference implementation is L2 today]
   L3  MACHINE:  L2 + a signed kit.json manifest + --json checker.
   L4  AUTONOMOUS: L3 + a conformance test in the library CI asserting
                 manifest/checker/docs agree, + a registry entry.

   A library MAY advertise the highest level each KIT meets.


11.  Future Work

   o  kit.json manifest + a reference manifest->checker generator, so
      authors write rules once (Section 3.3).
   o  A type-aware checker that resolves the value's type to promote
      CANDIDATE findings to CERTAIN (Section 3.4f), eliminating the
      false-positive class.
   o  `migratectl`: fetch/verify/apply/chain across a registry
      (Sections 6, 7, 13).
   o  Signed KITs and agent-side verification (Section 8).
   o  Opt-in adoption telemetry so an author sees which consumers are
      migrated (privacy-preserving; consumer-controlled).
   o  IDE quick-fix and dependency-bot integrations (Section 7).


12.  Security Considerations

   A KIT is executable content (a checker) plus instructions that edit a
   consumer's source. The threat is a malicious or corrupted KIT running
   in a consumer's repo/CI. Mitigations: signing + verification (8),
   read-only discovery (3.4a), the no-merge/least-trust guarantees (8),
   and the requirement that KITs carry no secrets or server internals
   (3.2). An AGENT MUST treat a KIT that fails signature verification as
   untrusted and refuse to execute it.


13.  Registry Considerations  [SPEC]

   A future registry maps (library, from, to) -> KIT location + digest +
   signature + conformance level. It is the discovery substrate for
   `migratectl` and for bots. Entries are published by the library
   author as part of release; the registry stores metadata, not the KIT
   bytes (which live in the library's release tree).

   Location: migrations/v0.9.2-to-v0.10.0/. Level L2. Exercises all five

   Reference AGENT: the "migrationbot" Claude Code agent in .claude/

Appendix B.  Example Manifest (kit.json)  [SPEC]

   {
     "lmkap": "1.0",
     "library": "github.com/ab0t-com/auth-sdk-go",
     "from": "0.9.2", "to": "0.10.0", "language": "go",
     "verify": ["go build ./...", "go vet ./...", "go test ./..."],
     "rules": [
       { "id": "events-url",  "type": "rename",
         "scope": "EventSubscriptionCreate|EventSubscription*",
         "from": ".URL", "to": ".Endpoint", "confidence": "candidate",
         "why": "server field is endpoint; url was never accepted" },
       { "id": "health-ts",   "type": "retype",
         "scope": "HealthCheckResponse.Timestamp",
         "fromType": "string", "toType": "float64",
         "example": 1787894650.69, "confidence": "certain",
         "why": "wire value is a JSON number; string failed whole decode" },
       { "id": "authorize",   "type": "behavioural",
         "scope": "Client.Authorize(resource)",
         "review": "now makes a real scoped decision and fails closed",
         "autoApply": false }
     ]
   }


Appendix C.  Example Worklog entry

   ## 2026-08-29 12:04 — CHECK
   claimed: locate v0.10.0 findings in ./
   did: ran migrate-check.sh . -> 13 candidate sites (8 .Timestamp, 5 .Enabled)
   verified: exit 1; list captured below

   ## 2026-08-29 12:07 — FIX + BUILD
   claimed: apply only the SDK-typed sites
   did: 0 edits — all 13 are on our OWN types (cache.Enabled, event.Timestamp)
   verified: go build ./... OK, go vet OK -> the build proves they were false
             positives (P5). migrate-check.sh . residual = informational only.
